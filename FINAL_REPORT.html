Retrieval-Augmented Generation over Five NLP Research Papers

Generative AI Fundamentals — Final Report

Author: Ankit Goel
Source documents: Transformer, BERT, RoBERTa, T5, GPT-3 (arXiv)
Stack: Python, FAISS, Ollama (llama3.2 + nomic-embed-text) — all running locally

1. Overview

I built a question-answering bot that answers questions about five NLP research papers. It remembers the last four turns of a conversation, so I can ask a follow-up question using "it" or "that" and it still knows what I mean.

The whole thing runs on my own machine. There is no cloud API and no API key. The models are served locally by Ollama.

What RAG is, and why I needed it

If you ask a language model a question directly, it can only answer from what it memorised during training. It has never seen my five PDFs. Worse, if it does not know something it will often make up an answer that sounds confident.

RAG fixes this by adding a search step before the model answers. First I search my own documents for the parts that look relevant. Then I paste those parts into the prompt and tell the model to answer using only that text. The model never "learns" my documents — every single time it answers, I hand it the relevant text fresh.

Question | | 1. search my documents -> 5 most relevant chunks | | 2. put those chunks + the last 4 turns + the question into one prompt | | 3. send that prompt to the language model v Answer

Figure 1. What happens each time someone asks a question.

Two models, two different jobs

This confused me at first, so I want to be clear about it. There are two models and they never talk to each other:

  • nomic-embed-text turns a piece of text into 768 numbers. It never writes sentences. Its only job is to make text comparable by maths, so similar text can be found.
  • llama3.2 reads the text that was found and writes the answer. This is the only part that actually understands language.

FAISS, the vector database, runs no model at all. It just compares numbers.

Why I did not use a framework

I wrote every stage myself in plain Python instead of using LangChain or LlamaIndex. The assignment does not require a framework, and writing it by hand meant I actually had to understand chunk boundaries, how retrieval maps back to text, how a prompt is built, and how memory is trimmed. If I had used a framework, most of that would have been hidden behind one-line function calls that I could not explain.

I did later build a second version using LangChain on a separate branch, to see what the trade-off looked like in practice. That is discussed in section 4.

2. Technical Implementation

2.1 Extracting text from the PDFs

src/ingestion.py uses the pypdf library to pull the text out of each page.

The problem is that a PDF is a page-layout format, not a text format. When you extract text you also get everything that repeats on every page: the paper's running title, page numbers, footers. If I left that in, it would end up inside my chunks and get embedded as if it were real content.

Instead of writing a list of known headers to remove, I detect noise by how it behaves: any line that appears on 60% or more of a document's pages is treated as a header or footer and removed, no matter what it says. I also remove lines that are only a page number, using a regular expression. This works on any PDF without me having to tune it per document.

2.2 Chunking

src/chunking.py cuts the cleaned text into pieces. I cannot embed a whole 15-page paper as one vector — a single list of 768 numbers cannot represent that much, and even if it could, a search would only ever return "the whole paper" instead of the paragraph that actually answers the question.

Chunk size is a real trade-off. Too small and the chunk has no context and does not make sense on its own. Too big and its vector becomes an average of several ideas and matches nothing precisely. I settled on these values:

Table 1. Chunking settings.
SettingValueWhat it does
TARGET_WORDS250Stop adding to a chunk once it would go past this
MAX_WORDS400Hard cap on any single piece of text
OVERLAP_WORDS45Words repeated from the end of one chunk at the start of the next

I split on blank lines first, because a blank line usually means a paragraph break. But pypdf does not reliably preserve blank lines in every PDF, and on my first attempt one chunk came out at 4,926 words. So I added two fallbacks: if a block is still over 400 words, split it into sentences; if even one sentence is over 400 words (which happens with tables and formulas), chop it by word count. That guarantees nothing oversized ever reaches the next stage.

Why the overlap matters. Imagine a sentence landing exactly on a chunk boundary: "The base model uses 8 attention heads, | each with dimension 64." Without overlap neither chunk contains the full fact, and whichever one gets retrieved gives half an answer. Repeating the last 45 words at the start of the next chunk means the complete sentence survives in at least one of them.

The result is 398 chunks across the five papers, averaging 287 words each.

2.3 Embeddings and the vector database

src/vectorstore.py sends every chunk to the nomic-embed-text model through Ollama, which returns 768 numbers per chunk. I send them in batches of 32 rather than one at a time, which turns 398 HTTP requests into about 13.

I then normalise every vector to length 1. This means only the direction of the vector carries meaning, not its size — which is what I want, because I care what the text is about, not how long it is. Once every vector has length 1, the cheap calculation FAISS uses (inner product) gives exactly the same result as the standard similarity measure (cosine similarity).

For the index I used faiss.IndexFlatIP. "Flat" means it compares against every stored vector with no shortcuts, so results are exact. FAISS also offers approximate index types that are much faster on millions of vectors but give slightly wrong answers. With only 398 vectors, exact search is already instant, so there is nothing to gain by trading away accuracy.

One design detail worth calling out, because it caused me a problem later. FAISS only stores numbers. When you search it, it gives you back row numbers like 142 — it has no idea what text row 142 was. I rely on the fact that chunks.json is in exactly the same order the index was built in, so chunks[142] is the right chunk. There is no ID linking them, just matching position. It works, but it is fragile, and section 4 explains how it broke.

2.4 Integrating the language model

src/bot.py handles answering. Calling a language model turned out to be much less mysterious than I expected: Ollama runs a small web server on my machine at localhost:11434, and I just POST some JSON to it and read the JSON that comes back. It is an ordinary HTTP request.

The request body uses the standard chat format, which is a list of messages each having a role:

[{"role": "system",    "content": "answer only from the given context..."},
 {"role": "user",      "content": "what is BERT?"},
 {"role": "assistant", "content": "BERT is..."},        <- an earlier reply
 {"role": "user",      "content": "how is it trained?"}]

The system message holds my standing instructions: answer only from the provided context, say so explicitly if the context is not enough rather than guessing, and cite the source as [doc_id, page X].

For each question I retrieve the top 5 chunks, join them into one labelled block of text, and put that into the prompt along with the question. The model makes exactly one call per question. It never sees the five chunks as five separate things — by the time it reads the prompt it is just text, like someone pasting five excerpts into a chat.

2.5 Conversational memory

The important thing I learned here is that the model has no memory of its own. Every call is independent. "Memory" simply means I resend the earlier turns as part of the next prompt.

I store the last four question-and-answer pairs in a collections.deque(maxlen=4). A deque with a maximum length automatically throws away the oldest item when you add a fifth, so that one line is the entire memory implementation — there is no "if there are too many, remove the first one" code to get wrong. The assignment asks for the last 4 interactions, and this says that directly.

To check it actually worked I added a line printing how many turns are held. Watching it climb 0, 1, 2, 3, 4 and then stay at 4 forever is much more convincing than asking the bot what it remembers, because the bot's own answer about its memory is not reliable evidence.

3. Evaluation

3.1 The 10 test questions

I wrote 10 questions covering all five papers. Four of them are deliberately written as follow-ups that use a pronoun instead of naming the paper, so they can only be answered correctly if memory is working. For example question 3 asks about the Transformer, and then question 4 asks "How many attention heads does that model use?" — nothing in question 4 says Transformer.

All 10 questions run through one continuous conversation, not a fresh one each time. This matters: a fresh session per question would start with empty memory every time, and the follow-up questions would never actually test anything.

3.2 Why I designed my own metric

The assignment allows either an established framework (RAGAS, Trulens) or my own metric, as long as I document the criteria and methodology clearly. I chose my own metric, but only after genuinely trying RAGAS and finding it did not work on my setup. That whole investigation is in section 4.3, because I think the reason is more interesting than the decision.

3.3 How the scoring works

There is no automatic way to check whether an answer written in English is "good". I cannot compare it to an expected string, because a dozen different wordings could all be correct. So I use the technique known as LLM-as-judge: I ask a language model to grade the answer, the way a teacher marks an essay against a rubric.

This means two separate model calls per question:

  1. The bot answers the question (this is the system being tested).
  2. The model grades that answer, given the question, the source chunks that were retrieved, the memory that was available at that moment, and the answer itself.

The judge is given a rubric and asked to score 1 to 5 on each of the four criteria the assignment names, with a one-sentence justification for each. The rubric is written out in full in JUDGE_SYSTEM_PROMPT in src/evaluate.py. In short:

Table 4. Scoring criteria (1 = poor, 5 = excellent).
CriterionWhat the judge is asked
RelevanceDoes the answer directly address what was asked?
AccuracyIs the answer consistent with the retrieved context specifically — not with the judge's own general knowledge?
Contextual AwarenessIf the question used a pronoun referring to an earlier turn, did the answer resolve it correctly?
Response QualityIs it clearly written, well organised, and appropriately detailed?

The accuracy criterion is worded carefully on purpose. I tell the judge to check the answer against the retrieved chunks only. If the answer states something true in general but not supported by the retrieved text, it should be marked down — because that would mean my retrieval failed and the model answered from memory instead.

Everything is written to data/eval/results.json: every question, the answer, the five retrieved chunks with their similarity scores, the memory available at that turn, and all four scores with justifications.

The memory questions worked. It correctly resolved "that model" to the Transformer from the previous turn, and cited the page.

I want to be honest about these numbers rather than just presenting them. The same model, llama3.2, both writes the answers and grades them. That is not an independent check. A model may well be gentler on its own phrasing than a different model would be, and that is a plausible reason the scores sit so close to the ceiling. If I were doing this again with more time I would use a separate, larger model as the judge.

4.2 Challenge: Ollama was silently cutting my prompts short

This was the most serious problem I found, and I only found it late.

Ollama has a setting called num_ctx, the context window, which defaults to 2048 tokens. I had never set it. I measured what my prompts actually come to: my chunks average 287 words, so 5 retrieved chunks is roughly 1,400 tokens; add the system prompt, the question, and four turns of conversation memory and a full prompt comes to about 2,100 tokens.

That is over the limit. And Ollama does not raise an error when a prompt is too long — it silently cuts off the oldest part. So on exactly the later questions where memory matters most, part of my conversation memory was being thrown away before the model ever saw it, and nothing anywhere reported a problem.

I fixed it by setting num_ctx to 8192 explicitly, and confirmed it took effect by checking Ollama's own /api/ps endpoint, which now reports context_length: 8192. The lesson I took from this is that a library default being wrong for your use case will not necessarily announce itself.

4.3 Challenge: RAGAS could not produce scores on my machine

I was asked to target four specific RAGAS metrics with minimum thresholds: Faithfulness above 90%, Answer Correctness above 80%, Context Recall above 85%, and Context Precision above 80%. I made two serious attempts and could not get it working. This is what happened.

First attempt. Installing RAGAS broke immediately: it imports a Google Vertex AI class that the current version of langchain-community has moved, so it would not even import. I fixed that by pinning older, compatible versions of langchain and langchain-community. Then every job started timing out. The cause was that RAGAS sends many requests in parallel by default, which is fine against a cloud API but not against Ollama on my laptop, which handles one generation at a time. Everything was queuing up and expiring while it waited. I fixed that too, by telling RAGAS to run one request at a time. After all of that, a 2-question test took 55 minutes and still returned "nan" (no score) for several metrics.

Second attempt. The first attempt had a fair weakness as evidence: I had not tuned Ollama at all. It was reloading the model between calls, and running at that 2048-token default, which would truncate RAGAS's prompts — and RAGAS's prompts are long, because each metric ships worked examples inside it. So I rebuilt it properly and checked each setting actually reached Ollama:

context_precision    100.0%  (need >80%)  PASS

Three of the four metrics failed with a parsing error, where llama3.2 either produced an opening brace and stopped, or repeated RAGAS's instructions back instead of following them. One metric exceeded even the 15-minute timeout. The run took about 25 minutes for two questions, which works out to roughly four to six hours for all ten.

The detail that told me what was really wrong: the only metric that worked, Context Precision, is also the only one of the four that does not ask the model to generate complicated structured JSON. Every metric that asked llama3.2 to break text into schema-shaped JSON statements failed. The one that did not, passed.

So the problem is not configuration — I tested and eliminated every configuration explanation. The problem is that llama3.2 is a 3-billion-parameter model, and RAGAS was designed and tested against large cloud models like GPT-4. Its metrics also chain several model calls together per question, which is cheap against a fast cloud API and very expensive against a small model running on a CPU.

Given that three of the four required metrics returned no score at all — not a low score, no score — I could not honestly report RAGAS numbers. I used my own documented metric, which the assignment explicitly allows, and it produces a complete set of results in about 20 minutes.

I should be clear about what this costs me. The two sets of four criteria are not the same things:

Table 7. The two sets of criteria are different measurements.
Assignment's four aspects (my metric covers these)RAGAS's four metrics (not covered)
RelevanceFaithfulness

The real capability I am missing is that Context Recall and Context Precision measure retrieval quality on its own. My judge only ever sees the final answer, so it cannot tell the difference between "the model reasoned badly" and "retrieval handed it the wrong chunks". That is a genuine gap, not something I want to gloss over.

The one thing I did not get to test is a larger model. A 7 or 8 billion parameter model follows structured-output instructions much better, and I think that is the most likely way to make RAGAS work on a local setup.

4.4 Challenge: a retry that made things worse

After raising num_ctx, an evaluation run crashed with a 500 error from Ollama. Two separate mistakes were behind it.

First, my retry logic was wrong in a way I did not expect. A request timeout in the requests library is client-side only — Ollama carries on generating the response I stopped waiting for. So retrying straight away put a second generation running alongside the first, and two large context windows at once was enough to make the server fail. Raising num_ctx is what made this fatal; at 2048 it had been harmless. I fixed it by waiting 30 seconds before retrying, so the first request can finish and release its memory.

Second, and worse, that one failed call killed the whole run. The error travelled up past nine already-completed judgements and the process died before writing anything to disk. About twenty minutes of work was lost because of one bad HTTP response. I changed the judge to catch the failure and record that single question as unscored instead. One missing score is a footnote in the results; an aborted run is a lost afternoon.

4.5 Challenge: my chunk and index files went out of sync

I mentioned in section 2.3 that FAISS returns row numbers and I rely on chunks.json being in the same order. That fragility bit me.

My generated data files are excluded from git because they can be rebuilt. When I switched between branches, git did not restore them — so I ended up with a chunks.json from one version paired with a faiss.index from another. Different chunk counts, different fields.

It crashed with a clear error, which I was lucky about. If the two versions had used the same field names and only the order had differed, there would have been no error at all — every answer would just have cited the wrong source, silently. The fix is simple (always regenerate both files together), but it showed me concretely why linking two files by position rather than by ID is risky.

4.6 Building the same thing with LangChain

Out of interest I rebuilt the pipeline using LangChain on a separate branch, keeping all LangChain code in a single file so the rest of the project did not depend on it.

What it genuinely improved: my roughly 80 lines of chunking logic became one configured splitter object, and LangChain's FAISS wrapper stores the vectors and the text together, which removes the fragile position-matching problem from section 4.5 entirely.

What it did not improve: my header and footer detection and my section tagging have no LangChain equivalent, so they stayed exactly as they were. A framework removes the boilerplate, not the parts specific to your problem.

It also had costs. I hit three separate version conflicts getting the packages to work together. And one convenience method turned out to send all 527 chunks in a single HTTP request, which timed out, so I had to add batching back by hand — the same batching I had already written myself in the original version.

Usefully, the LangChain version is what led me to find the num_ctx bug in section 4.2, which I then fixed in the main version. I kept the hand-written version as my submission because I can explain every line of it.

4.7 What I would improve

  • Rewrite follow-up questions before searching. Right now retrieval uses only the literal words of the current question. If someone asks "what about its encoder?", the search does not know what "its" refers to, even though the model does when it writes the answer. Memory affects how the answer is written, but not what gets searched for.
  • Filter out weak matches. I always send exactly 5 chunks to the model, however poor the match. A minimum similarity score would stop irrelevant text reaching the prompt at all.
  • Use a different model as judge, to remove the self-grading bias described in section 4.1.
  • Retry RAGAS with a 7B model, which would probably fix the structured-output failures and give me the retrieval-quality metrics I am currently missing.

5. Conclusion

The system does what the assignment asked. It ingests five PDFs and cleans the extraction noise out of them, cuts them into 398 chunks with overlap, embeds those chunks and stores them in a FAISS index, retrieves the five most relevant chunks for any question, generates an answer with a local open-source model using only that retrieved text, and remembers the last four turns so follow-up questions work. It scores between 90% and 100% across the four required criteria on all ten test questions.

What I actually learned was mostly from the things that went wrong. Calling a language model turned out to be an ordinary HTTP request, not something mysterious. A model has no memory of its own — "memory" just means resending earlier turns. And the two most serious bugs I found, the silent prompt truncation and the retry that made a failure worse, were both invisible: nothing crashed and nothing was logged. I only found them by measuring what was really being sent rather than trusting that the defaults were sensible.

The RAGAS investigation was the same kind of lesson. I could have written that RAGAS was too slow and left it there. Testing each explanation properly and eliminating them one by one gave me a much better answer: the failure is the small model's ability to produce structured output, not the configuration, and the proof is that the only metric that worked is the only one that does not require it.
